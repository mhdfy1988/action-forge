# 动作工坊方向与后续计划

## 定位

动作工坊（Action Forge）面向2D游戏动作资产制作。目标链路为图片→视频→序列帧→游戏动作资产；当前完成视频之后的单动作处理链路，不把未来功能包装成已实现。

## 已实现

抽帧 / 帧处理 / 导出。整理和抠图自由切换，人工精修弹窗实时同步，最终PNG序列或精灵图集及JSON资产包。当前为本机网页，保留客户端单屏布局，不是已发布桌面应用。

## 讨论确认：跨动作一致性（尚未实现）

目标是同一角色的跑步、跳跃、攻击等动作切换时大小和位置一致，不是逐帧修正所有生成缺陷。

- 生成阶段：同一张角色基准图作为各动作视频的首尾参考，统一画布、角色朝向/大小/位置。实际生成服务是否支持首尾输入，接入时单独核对。
- 加工阶段：用首尾对应的基准状态检查；必要时对整组动作应用一次缩放和偏移，保留跳跃/攻击内部运动，不逐帧拉回地面或自动居中。
- 输出阶段：一套角色动作共用画布、裁剪范围、缩放比例和原点。不能各动作独立紧裁后撑满，否则会再次破坏一致性。
- 基准帧用于校准，是否保留在正式动画由动作需要决定；跑步循环不混入起止过渡帧。

例如第一个动作建立角色基准；第二个动作复用同一参考图生成，抽帧后校准整组；第N个动作仍对齐该基准，所有动作一起验证范围和导出。首尾一致不能保证生成模型完全保持角色外观，明显漂移应先在生成视频检查。

## 建议阶段

1. 先试用并收束新版单动作导出，完成代码/文档/GitHub基线。
2. 项目保存与恢复、同一角色的多动作容器；先明确原图、视频、源帧、编辑和派生结果的持有关系。
3. 参考图/基准帧校准、整组缩放偏移及共用输出规格。先可视叠图手动对齐，再评估自动校准。
4. 图片生成视频接入与统一工作流；外部服务、隐私、费用及首尾帧支持需用户选择，不默认上传。
5. Godot/JS引擎适配与桌面客户端。当前JSON是中立描述，不能称为引擎原生资源。
