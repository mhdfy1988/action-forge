# 角色项目保存与恢复协议（R0-B）

## 状态与边界

R1已按本协议实现 `ProjectRepository` 与独立角色工作区的“打开/保存”能力。现有抽帧任务缓存、整理会话和批量抠图缓存只提供迁移输入，不持有长期编辑真值；项目清单与复制后的不可变素材才是重启后的恢复依据。项目清单结构见[角色资产协议](character-asset-protocol.md)。

## 文件持有

| 路径 | 持有者 | 规则 |
| --- | --- | --- |
| `project.json` | 项目仓库 | 唯一编辑清单；不从缓存反推覆盖。 |
| `assets/characters/.../source/` | 项目仓库 | 导入时复制原图或视频；原文件内容不修改。 |
| `assets/characters/.../matting/` | 项目仓库 | 抠图基底的不可变版本。 |
| `assets/characters/.../current/` | 项目仓库 | 精修结果的不可变版本；保存新版本时使用新文件名。 |
| `generated/` | 导出/引擎适配器 | 派生物，可删除重建，不允许清单引用。 |
| 旧`cache/`或浏览器内存 | 旧链路 | 只作为迁移输入；重启后不能保证存在。 |

清单中的路径仅可使用安全项目相对路径。运行时还要对实际文件做`resolve()`、确认仍位于项目根目录内并拒绝指向外部的符号链接/重解析点；路径字符串校验不能代替文件系统校验。打开工程时逐个核对必需源素材是否存在、可解码，缺失要明确列出路径，不能静默切回旧缓存。

## 保存事务

项目仓库提供列出、创建、加载和按`expectedRevision`保存的统一入口；编辑器不直接拼装`project.json`。当前实现使用 `filelock` 的跨进程锁保护每个项目，库API只存在于文件系统基础设施层，不污染角色领域模型；不使用普通内存锁冒充跨进程保障。

1. 读取并校验当前`project.json`，对比`expectedRevision`；不一致返回`REVISION_CONFLICT`，不写盘。
2. 对待保存清单做运行时校验，检查所有引用路径的归属和目标资产；写入中新图片使用不可变文件名，例如`frame_000001.r0002.<随机ID>.png`，不覆盖旧清单引用的文件。
3. 新二进制先写同卷临时文件、刷新内容并原子改名到最终资产路径。此时新文件尚未被清单引用，失败只留下可回收孤儿，不影响旧工程。
4. 将合法新清单写为同目录临时文件，刷新并关闭；只在全部新资产到位后原子替换`project.json`。替换失败则保留旧清单与旧资产，不报告保存成功。
5. 成功替换后才更新内存修订并发布项目变更消息。被新清单引用的资产不可在清单提交前删除；孤儿清理由独立维护操作完成，不参与本次事务。

每次成功保存项目`revision +1`；修改角色或其子项时对应角色`revision +1`；修改动作或其帧/事件时对应动作`revision +1`；帧像素或单帧编辑数据变化时该帧`revision +1`。未修改的兄弟动作、帧修订不变。清单中的修订由项目仓库统一计算，客户端不得直接提交自增后的数字。

## 失败与恢复

| 失败点 | 磁盘状态 | 恢复动作 |
| --- | --- | --- |
| 校验或修订冲突 | 旧清单、旧资产未变 | 保留内存草稿，显示冲突/错误。 |
| 新图片写入中断 | 旧清单有效，可能有临时文件 | 下次打开忽略临时文件；维护时清理。 |
| 新图片就位、清单未替换 | 旧清单有效，可能有孤儿新图片 | 忽略孤儿；不从文件名猜“最新版本”。 |
| 清单替换成功、回执前中断 | 新清单有效 | 重新打开按磁盘修订恢复；重试保存先比较修订，不能重复提交。 |
| 清单损坏或素材缺失 | 不静默降级 | 明确报错及路径；只读诊断，恢复必须由用户选择备份或修复。 |

Windows上替换文件可能因外部进程持有句柄而失败；这属于显式保存失败，不能偷偷改为直接覆盖写。R1已用故障注入覆盖替换失败保留旧清单，并覆盖重启回读、旧修订冲突和外部锁冲突；提交成功但回执丢失按重新加载磁盘修订恢复，不从临时文件猜测成功状态。

## 第一版不做

- 不做自动跨设备同步和云端冲突合并。
- 不做对`generated/`的备份保证；它应能从项目重新生成。
- 不使用数据库替代项目清单；如果以后项目体量证明JSON不够，再通过显式格式迁移引入。
