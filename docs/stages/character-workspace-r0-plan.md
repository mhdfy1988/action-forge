# R0 角色工作区准备计划

状态：这是已完成的R0历史计划；结果及当时的R1准入见[R0门禁](character-workspace-r0-gate.md)。其后的R1项目仓库、迁移器和独立角色工作区现已实现；共享画布与引擎连接仍分别属于R2/R3。

## 目标

在不修改当前单动作默认入口的前提下，为新版角色工作区建立可实现、可迁移、可测试的基础设计。R0只完成依赖边界、领域协议、持久化与迁移方案，不实现多动作界面，也不宣称已经接入游戏引擎。

## 当前实现基线

当前代码规模仍可维护，风险主要来自状态边界，而不是文件数量：

- `web/app.js` 负责当前页面总状态和工作区切换，同时串联整理、抠图与导出。
- `web/organizer-ui.js`、`web/matting-ui.js`、`web/export-ui.js` 已按功能拆分，但通过当前会话快照互相衔接。
- `app/main.py` 是本机HTTP组合入口。
- `app/service.py` 的 `Store` 面向当前视频、任务和缓存生命周期，不等价于可长期恢复的项目仓库。
- `app/domain.py`、`app/organizer.py`、`app/export_frames.py` 以及前端 `*-core.js` 中存在可以继续复用的领域与图像能力。

因此，新版不复用 `web/app.js` 的全局状态，也不把角色项目持久化塞进现有 `Store`。复用应发生在领域函数、服务接口和显式适配器层。

## 能力依赖与处理方式

| 当前能力 | 当前主要入口 | R0处理决定 |
| --- | --- | --- |

| 帧整理 | `app/organizer.py`、`web/organizer-core.js`、`web/organizer-ui.js` | 复用纯规则；定义动作帧顺序和修订接口，UI适配后接入。 |
| 批量抠图 | `app/batch_matting.py`、`web/matting-ui.js` | 复用后端处理协议；输入改为明确的动作修订快照，禁止从全局当前会话猜测。 |
| 人工精修 | 精修嵌入页与 `web/matting-ui.js` | 保留独立编辑器；为角色动作定义显式打开、自动同步和关闭确认协议。 |
| 统一导出 | `app/export_frames.py`、`web/export-core.js`、`web/export-ui.js` | 复用像素变换和图集组合；角色资产层负责汇总多个动作与共享坐标。 |

| 当前缓存与任务 | `app/service.py::Store` | 继续服务临时任务；新增项目仓库接口管理长期项目，不把两种生命周期混在一起。 |

## 计划中的模块边界

以下是职责边界，不是本轮已创建的代码目录；实际命名在开始实现时通过现有导入检查确认。

### 角色资产核心

- `CharacterProject`：项目身份、格式版本、项目修订和角色集合。
- `CharacterAsset`：角色基准图、共享画布、稳定原点和动作集合。
- `ActionClip`：动作名称、循环、帧率、动作级变换、帧和事件。
- `ActionFrame`：稳定帧身份、顺序、时长、启用状态和素材引用。
- `ActionEvent`：发生帧、事件类型和项目中立参数。

核心对象不得引用DOM、FastAPI、Godot类或浏览器文件句柄。

### 项目仓库

- `ProjectRepository` 是项目保存与加载的唯一接口。
- 文件系统实现只允许操作已登记的工作区根目录。
- 保存采用“写临时文件 → 校验 → 原子替换”。
- 项目修订和动作修订分别递增；旧修订写入显式冲突，不自动覆盖。
- 当前 `Store` 只提供临时任务和缓存，不能作为长期项目真值。

### 旧能力适配层

- 把角色动作快照转换为现有抽帧、整理、抠图和导出输入。
- 把现有结果映射回动作资产，但不能修改原始素材。
- 适配失败显式返回错误，不静默切换旧页面或旧格式。

### 新版角色工作区

- 独立路由，例如 `/studio/`；最终路径由实现评审确认。
- 独立状态容器，仅持有当前项目、当前角色、当前动作和各自修订。
- 一次只激活一个动作编辑会话；切换前保存或明确放弃当前未保存修改。
- 工作区状态由数据是否存在计算，不设置“整理结束”之类强制流程门槛。

### 引擎适配层

- 项目中立运行时快照是Godot和JavaScript的共同输入。
- 实时预览桥只监听本机，使用修订号丢弃迟到消息。
- 临时预览不写正式游戏工程；正式应用需要明确目标目录和单独操作。

## R0工作包

### R0-A 术语与领域协议

- 统一“角色资产、动作片段、动作帧、角色基准、稳定原点、动作事件、派生产物”的中文口径。
- 编写 `formatVersion: 1` 的角色项目示例JSON。
- 定义必填字段、稳定ID、相对路径、修订和未知字段策略。
- 定义角色级、动作级和单帧级参数的覆盖顺序。

交付物：角色资产协议草案、合法样例、最小非法样例。

### R0-B 文件持有与持久化

- 明确原视频、源帧、抠图结果、精修结果、预览缓存和正式产物分别由谁持有。
- 决定项目是否复制原视频；第一版至少保证源帧和编辑结果不依赖临时缓存恢复。
- 设计项目目录、原子保存、读回校验和损坏提示。
- 明确会话内撤销与跨重启恢复的边界。

交付物：项目目录样例、保存状态表、恢复与错误规则。

### R0-C 旧单动作迁移

- 把一个现有单动作结果映射成默认项目、默认角色和默认动作。
- 保留帧ID、来源、顺序、抠图修订和精修结果。
- 明确无法迁移字段的提示，不虚构缺失的角色基准或原点。
- 迁移重复执行应得到相同结果，不能重复复制或改写源素材。

交付物：迁移映射表、示例输入输出、幂等性测试设计。

### R0-D 运行时预览协议

- 定义完整快照与增量消息。
- 消息至少包含项目、角色、动作、修订、画布、原点、帧率、循环和动作级变换。
- 定义连接、加载、补丁、确认、冲突、断开和重连状态。
- 正式应用协议与实时预览协议分离。

交付物：消息样例、状态序列和错误码草案。

### R0-E 验证门禁

- 领域协议使用成熟运行时校验库或后端Pydantic模型验证，不只依赖注释和前端对象。
- 同一合法项目序列化后读回应等价。
- 未知版本、重复ID、越界路径、旧修订和缺失素材显式失败。
- 当前单动作测试保持通过；R0不得改变当前页面行为。

交付物：测试清单和后续R1实施准入结论。

## 状态变化

### 项目状态

```text
未打开 → 已加载 → 有未保存修改 → 保存中 → 已保存
                         └──────→ 保存失败
```

- 保存失败保留内存修改和旧磁盘版本。
- 保存成功后磁盘版本与内存修订一致。
- 外部文件修订高于当前修订时进入冲突，不自动覆盖。

### 动作会话

```text
未选择 → 加载动作 → 可编辑 → 有未保存修改
                       ├─ 保存 → 可编辑
                       └─ 放弃 → 重新加载已保存版本
```

整理、抠图、校准和预览是同一动作的能力状态，不是必须按顺序完成的阶段。

### 引擎预览

```text
未连接 → 连接中 → 已连接 → 同步快照 → 实时补丁
             └→ 连接失败              └→ 修订冲突/重发快照
```

## 第一条纵向验收场景

使用同一角色的 `run` 和 `jump` 两个动作：

1. 创建角色并添加两个动作。
2. 两个动作分别保存帧率、循环和动作级偏移。
3. 关闭并重新打开项目，所有身份和参数保持一致。
4. 修改 `jump` 不改变 `run`。
5. 两个动作使用同一画布和原点生成运行时快照。
6. Godot预览场景接收快照并切换动作；此步骤属于R3，不作为R0完成条件。

R0的退出条件止于第5步所需协议、持久化和测试设计全部明确；不得因为文档完成就宣称前5步代码已经可用。

## 执行顺序

1. R0-A：先定术语和领域协议，避免后续接口反复改名。
2. R0-B：确定文件持有和项目仓库，不让新版继续依赖临时缓存。
3. R0-C：定义旧数据迁移，保护现有成果。
4. R0-D：在核心模型稳定后定义引擎预览协议。
5. R0-E：完成门禁评审后进入R1代码实现。

每个工作包完成后单独更新当前任务；R0全部通过前不建立多动作界面，不改默认入口，不创建Godot正式工程写入功能。
